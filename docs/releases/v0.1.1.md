# v0.1.1 Release Contract

## Release Goal

**Theme:** Build the household balance sheet.

v0.1.1 establishes the local data model and application architecture that later portfolio, history, analytics, and automation releases will extend. At release, a user must be able to answer: “What does our Household own, owe, and have as net worth?”

This document owns v0.1.1 scope, status, and acceptance. Stable business rules live in the [domain model](../architecture/domain-model.md); database and command guarantees live in [data and IPC contracts](../architecture/data-and-ipc-contracts.md).

## User Stories

- As a new user, I can create one Household, select its base currency, and add one or more Members in a single onboarding flow.
- As a Household member, I can maintain Members, Institutions, and Groups without losing archived references.
- As a user, I can add an asset or liability with a Category, exact Ownership, an optional Institution and Group, and an initial value.
- As a user, I can edit Account metadata, append a new current value, and archive or restore the Account.
- As a user, I can see assets, liabilities, net worth, and allocation by Category, Member, Institution, and Group.
- As a user, I can browse all, sole-owned, and Shared Accounts and combine Category, Institution, and Group filters without losing state on refresh or detail navigation.
- As a user, I can use English or Simplified Chinese and select System, Light, or Dark appearance without restarting.
- As a user, I can assign local avatars and logos without granting broad filesystem access to the frontend.
- As a user with an unsupported future database, I see a safe blocked-startup page and the application writes nothing.

## Included

### Application

- First-run onboarding and one main window
- Sidebar and route-based navigation
- Window-state restoration
- Runtime English and Simplified Chinese localization
- System, Light, and Dark appearance
- Loading, error, empty, and blocked-startup states

### Household and References

- Create-once Household with name and base currency
- Household name update and settings display
- Member create, read, update, archive, restore, and avatar
- Institution create, read, update, archive, restore, and logo
- Group create, read, update, archive, restore, built-in icon, color, and custom logo

### Accounts

- Create, list, detail, update, archive, and restore
- Cash Equivalent, Investment, Property, Receivable, and Liability Categories
- Balance and Manual Value modes according to Category policy
- Immutable TrackingMode after creation
- Exact sole or shared Ownership
- Initial and appended current values
- Optional Institution, Group, note, logo, dates, and statistic-inclusion flags
- URL-backed owner, Category, Institution, and Group filters
- No permanent-delete UI, command, or repository operation

### Overview

- Account count
- Assets, liabilities, and net worth
- Allocation by Category, Member, Institution, and Group
- Backend-only authoritative financial calculation
- Consistent read snapshot and deterministic results

## Excluded

The release does not implement Instruments, Holdings UI, live prices, cryptocurrency providers, FX conversion, Transfers, Buy or Sell, an Activity ledger, historical charts, investment performance, cost basis, TWR, XIRR, automation, import, user backup, cloud sync, bank sync, or broker APIs.

Schema and domain placeholders for future concepts do not make those features part of v0.1.1.

## Remaining Phase 9 Contract

### Media

- Add native command flows to set or clear Member avatars and Institution, Group, and Account logos, plus a safe media read path.
- Use the native dialog boundary for file choice; do not expose arbitrary filesystem reads to frontend code.
- Validate type and size, decode safely, normalize orientation and metadata, resize to bounded dimensions, encode canonically, and persist atomically.
- Preserve the existing Group icon and color behavior; a custom logo is an additional option.
- Render absent or invalid media with deterministic fallbacks.

### Household and Settings

- Add typed commands and UI to read and update Household name and application settings.
- Base currency remains the onboarding currency once Accounts exist; v0.1.1 does not convert existing values.
- Allow `system`, `en`, and `zh-CN` language settings.
- Allow `system`, `light`, and `dark` appearance settings.
- Apply language and appearance changes immediately without restart.
- Keep English and Simplified Chinese locale keys synchronized.

### Phase 9 Acceptance

- Each entity can set, replace, clear, persist, and reload its supported avatar or logo.
- Invalid, oversized, or undecodable input returns a safe error and writes nothing.
- Replacing one reference does not break another entity that uses the same MediaAsset.
- Language and appearance survive restart and update the open window immediately.
- New capabilities and CSP changes are minimal and covered by focused review.

## Remaining Phase 10 Contract

Phase 10 closes cross-feature and distribution risk; it does not absorb unfinished feature correctness.

- Run the full automated regression suite and resolve all warnings that affect release quality.
- Recheck archive-reference retention, last-active-Member concurrency, exact Ownership, immutable TrackingMode, and Overview rounding.
- Recheck unsupported-future-database zero-write behavior.
- Define and test a recoverable pre-migration snapshot policy before shipping migrations beyond the initial schema.
- Audit production CSP, Tauri capabilities, native plugins, generated IPC, and log redaction.
- Complete keyboard-only critical flows and a VoiceOver smoke test.
- Verify empty, loading, pending, validation, conflict, and startup-error states across all routes.
- Build and launch the arm64 `.app` and `.dmg` on macOS 26 or later.
- Record signing and notarization state explicitly in release notes.

## Acceptance Criteria

v0.1.1 is complete only when all of the following hold:

### Data and Compatibility

- A fresh database is created, migrated once, and passes runtime integrity checks.
- Money never uses SQLite REAL or JavaScript/Rust binary floating-point in a financial contract.
- IDs, timestamps, currencies, Ownership, and Account Values satisfy the canonical domain rules.
- Account Values are append-only and latest-value ordering is deterministic.
- Only one Household can exist.
- Unsupported future databases and failed migrations never trigger destructive recovery or fallback writes.

### Core Workflows

- Onboarding creates the Household and Members atomically or writes no business rows.
- Users can maintain Household name, Members, Institutions, Groups, Accounts, and current values.
- Archive and restore preserve referenced historical identity and default-list behavior.
- Account creation and update reject invalid Category, Money, Ownership, currency, TrackingMode, or references atomically.
- A Household always retains at least one active Member.
- No permanent-delete action exists.

### Financial Results

- Assets and liabilities are stored as non-negative values, and only Liability Category contributes negatively.
- Excluded and archived Accounts do not affect Overview.
- Net worth and every breakdown match the backend golden fixture.
- Member percentages use asset ownership rather than net-worth contribution and remain within 10,000 basis points.
- The frontend performs formatting but no second financial calculation.

### Experience and Release

- Account filters survive refresh and list-detail navigation.
- Every primary workflow has loading, error, empty, validation, and pending behavior.
- English, Simplified Chinese, System, Light, and Dark work without restart.
- Critical flows are keyboard accessible and pass a VoiceOver smoke test.
- Media input is bounded, normalized, local, and safely displayed.
- Generated IPC, TypeScript strict checks, ESLint, frontend tests, Rust tests, formatting, Clippy, CSP, and capability audits pass.
- The arm64 application and disk image launch successfully on the minimum supported macOS version.

## Compatibility Promises

Future releases must preserve:

- Typed UUID identities and Household scoping
- Exact basis-point Ownership
- Decimal-string Money and non-negative persisted liabilities
- Append-only Account Value observations
- Archive and retained-reference semantics
- The separation of Account Value, future Activity, and future Instrument Quote
- Rust authority for persistence and financial calculations
- Local usability when network providers fail
- Pre-write blocking for unsupported future database versions

Future release details belong in new release contracts. The [roadmap](../product/roadmap.md) intentionally does not pre-decide their schemas or algorithms.
