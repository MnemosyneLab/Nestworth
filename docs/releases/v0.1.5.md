# v0.1.5 Release Contract

## Purpose and Status

**Release theme:** Sustainable Long-Term Use — keep Nestworth current, recoverable, and efficient without weakening its ledger.

**Status:** `Phases 0–12 locally validated; public distribution closeout pending`. Product scope and technical decisions remain approved by this document set. See the [release evidence](v0.1.5-release-evidence.md) for the exact tested arm64 artifact and remaining external gates.

v0.1.5 turns the v0.1.4 balance sheet, ledger, history, and analytics into a product that can be maintained for years. It adds review-before-post automation, a maintenance inbox, recoverable local backups, controlled data exchange, manually maintained benchmarks, and keyboard-focused navigation.

The detailed implementation contract is split between this release scope, the [technical design](v0.1.5-technical-design.md), the [implementation plan](v0.1.5-implementation-plan.md), and the [compatibility baseline](v0.1.5-baseline.md).

## Release Goal

A Household can keep routine records current with less repetitive input, identify stale facts, recover from device or database loss, move its data out in documented formats, compare portfolio return with a manually maintained benchmark, and reach common workflows quickly from the keyboard.

The central invariant is:

> Automation may prepare financial facts, but only an explicit user action may post an Activity or replace the active database.

Supporting invariants are:

> Backup is the only full-fidelity round trip. Export and CSV import are controlled interchange surfaces, not alternative restore mechanisms.

> A benchmark describes comparison performance. It never changes net worth, cost basis, gain, snapshots, or the Activity ledger.

## User Stories

- As a user, I can schedule routine deposits, withdrawals, transfers, income, fees, and debt payments as reviewable pending items.
- As a user, I can edit, skip, or post a due item without any rule silently changing my ledger.
- As a user, I can see which balances, cash observations, and manual quotes need review and temporarily snooze a reminder.
- As a user, I can create a portable local backup, inspect it before restore, and recover without overwriting my current database until validation succeeds.
- As a user, I can export documented machine-readable data and use strict Nestworth CSV templates for bounded bulk input.
- As an investor, I can maintain a benchmark level series manually or by CSV and compare its return with Nestworth TWR.
- As a keyboard user, I can search entities and Activities and invoke safe navigation or creation actions from one command palette.
- As an offline user, I can use every v0.1.5 capability without a provider, cloud account, or network connection.

## Included

### Review-Before-Post Automation

- User-created pending Deposit, Withdrawal, cash/position Transfer, Buy, Sell, Income, Fee, Debt Draw, and Debt Payment for a future or due local date.
- Recurring rules with daily, weekly, monthly, or yearly cadence, a positive interval, start date, and optional end date.
- Supported recurring kinds: Deposit, Withdrawal, same-currency cash Transfer, Income, Fee, Debt Draw, and Debt Payment.
- Explicit generation of due occurrences after startup or from the Maintenance page; no bootstrap write and no work while the application is closed.
- Editable pending facts until posting; terminal `posted` and `skipped` outcomes remain visible.
- Posting through the existing ActivityService in the same transaction that marks the pending item posted.
- Rule edits apply only to occurrences generated afterward. Existing pending items keep the copied rule revision.
- Archive and restore for recurring rules; archive generates no new occurrence and changes no existing pending item.

### Freshness Policies and Maintenance Inbox

- Household defaults and optional per-target overrides for:
  - Balance and Manual Value Account observations
  - Holdings-account cash observations
  - Manual Instrument Quotes
  - Manual FX Quotes
- Review intervals from 1 to 3,650 days or explicitly disabled.
- Rust-derived `current`, `due`, `overdue`, `missing`, and `snoozed` maintenance status.
- A Maintenance page that combines due pending Activities and valuation-review items.
- Snooze-until-local-date for a maintenance item. A new observation naturally resolves its reminder.
- Freshness affects labels and reminders only. A stale value remains a real observation and follows the existing valuation completeness rules.

### Backup and Restore

- A versioned `.nestworth-backup` bundle containing a consistent SQLite snapshot and a small JSON manifest with size and SHA-256 checksum.
- Streaming backup creation to an application-owned temporary path followed by an atomic move to the user-selected destination.
- Backup inspection that performs no write and reports format version, database migration, product version, creation time, Household display name, and checksum status.
- Restore to an application-owned staged database, followed by supported-schema fingerprint, migration compatibility, SQLite integrity, foreign-key, History Origin, ledger, projection, and declaration validation.
- Explicit restore confirmation after inspection.
- A timestamped, verified application-owned recovery Backup bundle of the current database before replacement, visible from Data Management and restorable through the same validation path.
- Atomic replacement or rollback. A successful restore closes the active database and requires application restart before further commands.
- Restore from schema `001` through `005`, migrating only the staged copy. A future database version is rejected without changing either database.
- Listing and inspecting application-owned recovery Backups without exposing their filesystem paths.

### Data Export and CSV Import

- Canonical JSON export version 1 containing documented user-authored durable facts, stable identities, timestamps, decimal strings, reference catalogs used by those facts, and media bytes.
- JSON export excludes reconstructible caches and derived results such as current projections that can be selected from observations, derived lots, gain, return, and snapshot rebuild progress. It is a data-liberation format and is not accepted by Restore in v0.1.5.
- RFC 4180 CSV export for Activities, manual Instrument Quotes, manual FX Quotes, and Benchmark observations.
- Strict Nestworth CSV import templates for:
  - Post-origin Activities accepted by `CreateActivityInput`, excluding Opening Adjustment, Reversal, and Correction
  - Manual Instrument Quotes
  - Manual FX Quotes
  - Benchmark observations
- Two-step import: side-effect-free preview followed by explicit commit against the same file SHA-256.
- At most 2,000 data rows per import. The entire accepted import commits once or writes nothing.
- Optional source namespace and external ID for deterministic duplicate detection. Same identity and same canonical content is skipped; same identity with different content is rejected.
- Import batch and row outcomes remain queryable without storing source paths or raw input files.

### Benchmarks and Relative Return

- Household-scoped Benchmarks with name, currency, `price_return` or `total_return` series kind, maximum carry window, and archive state.
- Append-only positive Decimal observations on local calendar dates, entered manually or through the Benchmark CSV importer.
- Latest observation for the same date selected by creation time and ID; prior observations remain evidence.
- One Household default Benchmark, with an explicit query-time override.
- Rust-computed benchmark return over the same closed-day period used by portfolio TWR.
- Foreign-currency Benchmark levels converted with eligible historical FX before calculating return.
- Excess return defined as portfolio cumulative TWR minus Benchmark cumulative return, expressed as percentage-point difference.
- Explicit unavailable diagnostics for missing endpoint levels, stale carry, missing FX, incomplete portfolio TWR, or incompatible period.

### Search and Keyboard Productivity

- Bounded Household-scoped search over Accounts, Instruments, Institutions, Groups, Members, and Activity notes.
- Stable result types, IDs, safe labels, optional short excerpts, archive state, and destination metadata returned by Rust.
- A global command palette opened with `Command+K`.
- Frontend-owned static actions for navigation and opening approved create, backup, import, and maintenance workflows.
- Search results may navigate to a record or apply a stable route filter; they never mutate data directly.
- Keyboard access, focus restoration, and non-conflicting shortcuts for primary v0.1.5 workflows.

## Excluded

v0.1.5 does not implement:

- Automatic posting, approval rules, unattended financial writes, or scheduled work while Nestworth is closed
- Recurring Buy/Sell, cross-currency Transfer, Adjustment, Manual Valuation, or Opening Adjustment
- Bank, broker, wallet, or credit-card synchronization
- Parsing arbitrary broker or bank statements, user-defined column mapping, OCR, or AI-assisted import
- Import of pre-origin transactions or conversion of a cost-basis declaration into an acquisition Activity
- JSON import, merge restore, selective restore, incremental backup, cloud backup, or multi-device sync
- Built-in backup encryption, password recovery, Keychain integration, or secret storage
- Automatic backup retention or deletion of user-selected backup files
- Live Benchmark, quote, or FX providers
- Benchmark dividends inferred by Nestworth; a `total_return` series must already include its provider's reinvestment convention
- Benchmark-based net worth, gain, lot valuation, asset allocation, or attribution
- OS notifications, menu-bar agents, launch agents, or background refresh
- Full-text indexing, fuzzy ranking dependencies, or search over raw financial amounts
- Command-palette execution of destructive confirmation, restore completion, Activity posting, reversal, or correction
- Tax reporting, new lot policies, corporate actions, planning, targets, or forecasting

## Locked Product Decisions

| Decision | v0.1.5 contract |
| --- | --- |
| Automation authority | Rules generate pending drafts only; no automatic posting |
| Posted Activity | Existing ActivityService remains the only financial write path |
| Future financial fact | Stored only as pending; `activities.effective_at` remains non-future |
| Recurring trade/FX | Deferred because execution price, destination amount, FX, and fee are not known in advance |
| Schedule timezone | Immutable confirmed History Origin IANA timezone |
| Monthly/yearly overflow | Clamp to the last valid local day; never skip silently |
| Rule edit | Applies only to not-yet-generated occurrences |
| Schedule edit | Anchor, cadence, and interval are immutable; archive the old rule and create a new one |
| Pending terminal state | Posted or skipped records are immutable; correction uses the ledger after posting |
| Freshness effect | Reminder/display state only; never changes value, completeness, snapshot, or analytics |
| Backup format | Versioned bundle with manifest and full SQLite snapshot |
| Backup encryption | Not included; UI must warn that the file contains private financial data |
| Restore safety | Inspect, stage, validate, confirm, recovery-copy, replace, restart |
| Recovery retention | Recovery Backups are never deleted automatically; Settings may restore them, and explicit Delete All Data removes application-owned copies |
| Future database | Backup may be inspected but a database newer than supported migration `005` cannot be restored |
| Full-fidelity round trip | Backup/Restore only |
| JSON export | Stable documented data-liberation format; not a restore input in v0.1.5 |
| CSV import | Strict Nestworth templates, maximum 2,000 rows, preview then atomic commit |
| Import identity | Optional source namespace plus external ID; conflicts never overwrite prior facts |
| Existing basis declaration | Preserved as a declaration; never imported or reclassified as a Buy |
| Benchmark source | Manual entry or strict CSV only |
| Benchmark identity | Currency and series kind are immutable; changing either creates a new Benchmark |
| Archived default Benchmark | Retained and resolvable with an archived badge; it cannot be newly selected while archived |
| Benchmark comparison | Cumulative Benchmark return and TWR percentage-point difference; never compared with XIRR |
| Benchmark currency | Historical direct/inverse FX conversion follows existing valuation rules |
| Search authority | Rust searches persisted entities; frontend filters only its static action registry |
| Financial authority | Rust only; frontend renders returned facts and non-financial geometry |
| Provider dependency | None |

## Acceptance Scenarios

### Recurring Salary Review

A monthly Income rule starts on January 31 for `5,000 SGD`. February generates one pending occurrence on February 28 or 29, not March 2 and not zero occurrences. Opening Nestworth does not post it. The user changes the actual amount to `5,100 SGD`, previews it through Rust, and posts it. One Income Activity and one pending-to-posted link commit together.

### Recurring Transfer Does Not Guess FX

A same-currency `1,000 SGD` savings Transfer may be recurring. A proposed CNY-to-SGD rule is rejected because the future received amount and execution spread are unknown. The user may create a cross-currency pending item manually after both native amounts are known, or post the existing cross-currency Activity workflow directly.

### Maintenance Reminder

An Account has a 30-day review interval and its latest value is 35 local days old. It appears as `overdue`; the value still participates in net worth under the existing rules. Snoozing until Friday hides it from the due list until Friday without writing an Account Value. Appending a new value resolves the reminder.

### Safe Restore

The user selects a schema-4 backup while the current database is schema 5. Nestworth verifies the manifest and checksum, copies the backup database to staging, migrates staging to schema 5, runs integrity and domain checks, shows an inspection summary, and asks for explicit confirmation. It then creates a timestamped recovery copy of the current database and replaces it. If replacement fails, the current database is restored and the command reports failure without presenting the staged data as active.

### Atomic Activity Import

A 100-row Activity CSV previews as 98 valid rows, one exact duplicate, and one invalid archived Account reference. Commit is unavailable until the invalid row is fixed or excluded by creating a new file. After correction, commit posts the 99 non-duplicate Activities in deterministic order and records the duplicate as skipped, all in one transaction. A second import with the same source namespace, external IDs, and content posts nothing.

### Benchmark Comparison

Portfolio TWR for a period is `4.04%`. The selected Benchmark has eligible base-adjusted endpoint levels `100` and `103`, so its return is `3%` and excess return is `1.04` percentage points. If the ending level is older than the Benchmark's carry window, all Benchmark and excess-return numbers are unavailable; portfolio TWR remains visible.

### Command Palette Safety

`Command+K` finds an Account, an Activity note, and the “Create backup” action. Selecting the Account navigates to detail. Selecting backup opens the backup workflow. No palette result can immediately delete data, restore a database, post a pending item, or reverse an Activity.

## Release Acceptance

v0.1.5 is complete only when:

- Migration `005` preserves every v0.1.1–v0.1.4 identity, financial row, declaration, snapshot revision, current total, lot replay result, and analytics golden.
- Migration `005` SQL alone creates zero recurring rules, pending items, imports, policies, reminders, Benchmarks, observations, Activities, quotes, or declarations.
- Unsupported future migration `006` receives zero application writes from every old and new command.
- A recurring rule never posts an Activity, and generation is idempotent by `(rule_id, scheduled_local_date)`.
- Future dates remain impossible in the posted Activity ledger.
- Posting a pending item writes its Activity, projections, dirty range, and terminal link once or writes nothing.
- Rule edits do not rewrite generated pending items; archived rules generate nothing.
- Rule anchor, cadence, and interval cannot change after creation; payload edits affect only later generation.
- Freshness policy and snooze changes do not alter valuation, snapshots, ledger, lots, declarations, gain, return, or attribution.
- Backup creation uses one consistent SQLite snapshot and verifies the written bundle checksum before success.
- Restore validates only staging, retains the current database until confirmation, creates a verified restorable recovery Backup, and rolls back a failed replacement.
- Restore rejects corrupt, malformed, unexpected-schema, trigger/view/virtual-table, structurally unsafe, wrong-product, and unsupported-future bundles without changing current data.
- JSON and CSV exports use deterministic schemas, canonical decimal strings, UTC timestamps, and safe file replacement.
- Import preview writes nothing; commit rechecks the file hash and all domain references.
- Import duplicate identity with changed content is a conflict, never an overwrite.
- Activity import posts only through ActivityService and cannot create a pre-origin or future Activity.
- A declaration remains a declaration through backup, restore, JSON export, and CSV workflows.
- Benchmark observations are append-only; comparison never changes financial state.
- Benchmark currency and series kind never change; archived retained defaults remain resolvable but archived Benchmarks cannot be newly selected or receive observations.
- Benchmark and excess return are withheld when an endpoint level, allowed carry, FX, or portfolio TWR input is unavailable.
- Search is Household-scoped, bounded, deterministic, escaped, and free of N+1 queries.
- Command-palette actions cannot bypass confirmation or invoke destructive/financial mutations directly.
- Frontend code performs no recurrence, balance, import, Benchmark return, FX, gain, return, or net-worth calculation.
- English and Simplified Chinese locales, generated bindings, frozen allowlist, CSP, capabilities, logging, and error shielding are current.
- Domain, migration, scheduling, pending-post, freshness, backup, restore, import, Benchmark, search, command, frontend, golden, and compatibility tests pass through `bun run check`.
- Isolated-data launch, keyboard navigation, VoiceOver, arm64 packaging, and the chosen signing/notarization policy pass the release gate.

## Compatibility Promises

v0.1.5 preserves every v0.1.1–v0.1.4 promise and adds:

- A pending item is not a financial fact and never appears in net worth, history, lots, gain, return, or attribution before posting.
- Posted Activity identity and semantics never depend on the rule or import that prepared it.
- Rule, pending, import batch, Benchmark, Benchmark observation, and Backup IDs remain stable.
- Restore never mutates the selected backup bundle.
- A v0.1.5 backup contains the complete active database, including media, ledger evidence, snapshots, declarations, automation, policies, imports, and Benchmarks.
- JSON export versions are immutable. A future exporter may add a new version but cannot reinterpret v1 fields.
- CSV templates are versioned. Unknown columns or enum values are rejected rather than ignored silently.
- Import provenance cannot be used to edit or delete the posted entity.
- Benchmark observations never become Instrument Quotes or FX Quotes, and vice versa.
- Benchmark comparison never changes the v0.1.4 definitions of TWR, XIRR, gain, or attribution.
