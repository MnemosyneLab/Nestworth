# v0.1.3 Compatibility Baseline

This document freezes the implemented v0.1.2 surface that v0.1.3 must preserve. It is evidence for Phase 0, not a product-decision forum. Later phases add schema `003`, Activity/history commands, and UI on top of this baseline without rewriting v0.1.2 business rows.

Executable truth remains the current migrations, tests, generated bindings, and frozen command allowlist. This file records those values so later work can detect drift.

## Schema Freeze

- Current maximum embedded migration is `002` (`001_initial.sql` plus `002_portfolio.sql`).
- v0.1.3 will add `003_activity_history.sql` in Phase 2. Migration SQL must create schema only. It must not rewrite v0.1.2 business rows, add triggers, or store financial facts as generic JSON.
- Existing Account Value, Account Cash, Instrument Quote, and FX Quote identities and timestamps remain unchanged. Holding Quantity is captured as current state, never backfilled as a trade.
- `account_values` and `account_cash_values` gain a nullable `activity_id` only in `003`. The sanitized v0.1.2 fixture must not contain that column.
- Unsupported future databases remain zero-write. `max_supported_migration` stays at `2` until Phase 2 lands `003`.

Sanitized fixtures:

- Released v0.1.1: `src-tauri/test-fixtures/v0.1.1.sql`
- Released v0.1.2: `src-tauri/test-fixtures/v0.1.2.sql`
- Activity and timezone goldens: `src-tauri/test-fixtures/v0.1.3-activity-goldens.md`

## Frozen Product Decisions

These are already approved in the [release contract](v0.1.3.md). They are frozen here so Phase 1+ does not reopen them:

- Raw legs remain internal. Every user command uses a tagged kind-specific input.
- Settlement currency equals Instrument quote currency in v0.1.3.
- Snapshots are append-only revisions and closed-day only.
- Future and pending Activities remain deferred.
- No live provider is selected or required. All Activity and history workflows remain manually operable offline.

## Expected Query Counts

Counts come from inspecting `ValuationSnapshot::load` and the `list_*_in_tx` helpers. None of these paths query per Account or per Holding in a loop. Duplicate snapshot loads in the current call graph are recorded as executions, not as additional families.

### Statement families used by current valuation reads

1. Household (`SELECT id, base_currency FROM households … LIMIT 1`)
2. Accounts plus latest Account Value (one windowed join; no N+1)
3. Ownership batch for the listed Accounts
4. Instruments (household-scoped, including archived when loading the snapshot)
5. Active Holdings for the household
6. Latest Account Cash by Account and currency
7. Latest Instrument Quotes by Instrument and source
8. FX quote preferences
9. Latest FX Quotes
10. Members (Overview catalog resolution, including archived)
11. Institutions (Overview catalog resolution, including archived)
12. Groups (Overview catalog resolution, including archived)

`ValuationSnapshot::load` always runs families 4–9 once per call: instruments, holdings, cash, instrument quotes, FX quotes, FX preferences.

### Overview (`get_overview`)

| Item | Count |
| --- | --- |
| Unique statement families | 12 |
| SQL executions in the current call graph | 19 |
| N+1 per Account | none |

Current execution order: household; accounts+latest values; ownership batch; household again inside `list_accounts_in_tx`; snapshot families 4–9 inside `list_accounts_in_tx`; snapshot families 4–9 again in `get_overview_in_tx`; members; institutions; groups.

### Portfolio (`get_portfolio`)

| Item | Count |
| --- | --- |
| Unique statement families | 9 (household, accounts+latest values, ownership, plus snapshot families 4–9) |
| SQL executions in the current call graph | 18 |
| N+1 per Account | none |

Current extras versus a single snapshot load: `list_accounts_in_tx` loads household and the snapshot once, `get_portfolio_in_tx` loads the snapshot again, and `required_fx_status` re-reads latest FX quotes and FX preferences.

### Account detail (`get_account`)

| Item | Count |
| --- | --- |
| Unique statement families | 9 (household, one Account row, latest Account Value, owners for that Account, plus snapshot families 4–9) |
| SQL executions in the current call graph | 11 |
| N+1 per Holding or cash row | none |

Account detail still loads the full household `ValuationSnapshot`. It does not query quotes, Holdings, or cash inside a per-component loop. `get_account` currently opens `BEGIN IMMEDIATE` even though the command is a read; that transaction shape is frozen as current behavior, not a Phase 0 change.

### Ledger and history reads

`N/A until Phase 6`. Planned query families from the technical design, each household-scoped and cursor-bounded rather than offset-paginated:

- History Origin header
- Origin baseline items (Account Value, cash, Holdings, Account state, Ownership, quote preferences)
- Activity list by `(effective_at, created_at, id)` cursor
- Activity filters (Account, Instrument, kind, classification, local date range)
- Activity detail plus ordered legs
- Reversal and correction-chain lookup
- Account timeline merge (origin, Activities, legacy observations, state changes)
- Latest effective-dated Account/Holding/preference observations at or before cutoff
- Historical Instrument Quote and FX Quote selection at or before cutoff
- Snapshot dirty-range state
- Snapshot headers by local date and revision
- Snapshot items by Account and Instrument
- Net-worth trend points plus the live current Overview point

Phase 6 must keep these bounded. Queries inside a loop over returned Activities, Accounts, or snapshot items remain prohibited.
