# v0.1.4 Compatibility Baseline

This document freezes the implemented v0.1.3 surface that v0.1.4 must preserve. It is evidence for Phase 0, not a product-decision forum. Later phases add migration `004`, analytics services, analytics commands, and the `/analytics` route on top of this baseline without rewriting v0.1.1, v0.1.2, or v0.1.3 business rows.

Executable truth remains the current migrations, tests, generated bindings, and frozen command allowlist. This file records those values so later work can detect drift.

## Schema Freeze

- Current maximum embedded migration is `003` (`001_initial.sql`, `002_portfolio.sql`, `003_activity_history.sql`).
- `max_supported_migration()` in `src-tauri/src/infrastructure/database_bootstrap.rs` derives its value from the embedded migrator, so it currently reports `3`. It becomes `4` only when Phase 2 lands `004`.
- v0.1.4 will add `004_analytics.sql` in Phase 2. Migration SQL must create schema only. It must not rewrite v0.1.1, v0.1.2, or v0.1.3 business rows, add triggers, or store financial facts as generic JSON.
- Migration `004` must not add columns to `activities` or `activity_legs`. Posted Activities are immutable evidence, and cost basis is a derived interpretation of that evidence rather than a new ledger fact.
- Unsupported future databases remain zero-write. Analytics reads must be blocked by the same state machine as Activity and history reads.

## Frozen Ledger Facts Available to v0.1.4

This section records exactly what v0.1.3 persists, because v0.1.4 cost basis must be derived from these facts and nothing else.

### Activity header (`activities`)

| Column | v0.1.4 relevance |
| --- | --- |
| `kind` | Closed 15-value enum; identifies acquisitions, disposals, and remeasurement |
| `effective_at`, `effective_local_date` | Lot acquisition ordering and period boundaries |
| `created_at` | Deterministic tie-break at equal effective time |
| `reverses`, `corrects`, `correction_group` | Identifies economically nonexistent Activities |
| `income_kind` | Nine-value enum including `dividend` and `interest` |
| `fee_kind` | Eight-value enum including `brokerage_commission` |
| `related_instrument_id` | Attributes Income, Fee, Buy, and Sell to an Instrument |

### Activity leg (`activity_legs`)

| Column | v0.1.4 relevance |
| --- | --- |
| `role` | `source`, `destination`, `holding`, `settlement`, `fee`, `income`, `liability`, `adjustment` |
| `direction` | `increase` or `decrease`; carries the sign |
| `component_kind` | `account_value`, `holdings_cash`, `holding_quantity` |
| `amount`, `currency` | Gross settlement amount and fee amount for monetary legs |
| `holding_id`, `instrument_id`, `quantity` | Lot quantity for Quantity legs |
| `fx_rate` | Derived transaction rate on cross-currency cash Transfer legs |
| `sort_order` | Stable order within an Activity |

### Recorded gaps

These are facts about the implementation, not proposals. v0.1.4 design must respect them.

- **Trade unit price is not a persisted column.** `TradeSpec` accepts `unit_price` and `src-tauri/src/domain/activity.rs` validates `gross_amount == quantity × unit_price` through `expected_gross`, but only the resulting `gross_amount` is stored, on the settlement leg. Unit price is recoverable only as `gross ÷ quantity`, which is exact only up to the four-fractional-digit Money rounding applied when the gross amount is constructed. v0.1.4 must derive lot cost from the persisted gross amount and must not treat a recomputed unit price as an execution fact.
- **A zero-gross trade persists no settlement leg.** `trade()` appends the settlement leg only when `gross_amount` is non-zero, so a confirmed zero-unit-price Buy produces a Quantity leg and an optional Fee leg only. Its lot cost is zero plus any explicit fee.
- **Trade fees carry no `fee_kind`.** `trade()` sets `related_instrument_id` and leaves `income_kind` and `fee_kind` null, so a brokerage commission recorded inside a Buy or Sell is identified by `role = 'fee'` and its parent Activity, not by `fee_kind`. A v0.1.4 fee breakdown must not assume `fee_kind` is present on every fee leg.
- **Trade settlement currency equals the Instrument quote currency.** Enforced in `trade()`. v0.1.4 lot cost currency inherits that constraint.
- **Acquisition FX is not persisted.** No trade stores the native-to-base FX rate at execution time. v0.1.4 currency decomposition must select it historically with the existing at-or-before-cutoff quote rule and must report `unavailable` when no eligible quote exists.
- **Debt principal and interest are already separate.** Debt legs use `role = 'liability'`; interest and charges use an explicit Fee leg.

### Frozen classification derivation

`classify(kind, role)` in `src-tauri/src/domain/activity.rs` is the single source of wealth-flow classification, and `src-tauri/src/application/history_repositories.rs` mirrors it in SQL for filtering. The closed set is:

```text
external_inflow
external_outflow
internal_transfer
trade_principal
income
fee
debt_principal
remeasurement
```

v0.1.4 adds scope-relative flow classification for return calculation. It must not change, extend, or reinterpret this eight-value enum, and it must not let a caller supply a classification.

## Frozen Application-Layer Shape

The application layer contains **no service struct**. `rg "pub struct .*Service"` over `src-tauri/src` returns nothing. Every `pub struct` in `src-tauri/src/application/` is a DTO or an input type.

A "service" is a module of free `pub async fn`s. The documentation names map to modules as follows:

| Documentation name | Module |
| --- | --- |
| ValuationService | `application::valuation_service` |
| ActivityService | `application::activity_service` |
| HistoricalValuationService | `application::historical_valuation_service` |
| History snapshot rebuild | `application::history_snapshot_service` |
| History queries | `application::history_query_service` |

Public entry points take `state: &AppState`. Transaction-scoped variants take `&mut Transaction` and carry an `_in_tx` suffix. Repository SQL is centralized in `application::history_repositories`. Shared transaction helpers such as `begin_read_tx` and `begin_write_tx` live in `application::reference`.

v0.1.4 must follow this convention. Introducing a service struct would be a new architectural pattern and is out of scope.

Other frozen implementation facts:

- `Classification` is not a persisted column. It is derived on read by `classify(kind, role)` and mirrored in SQL only for list filtering.
- Trade legs never carry `fx_rate`, and the `activity_legs` `CHECK` constraint forbids `fx_rate` on `holding_quantity` legs entirely. FX rates appear only on Transfer and Debt legs.
- `MAX_REBUILD_DAYS` is `366` in `application::history_snapshot_service`.
- `ErrorCode` in `src-tauri/src/error.rs` has 40 variants. `FORBIDDEN_TRACING_FIELDS` in `capabilities_test.rs` has 26 entries and already includes `amount`, `quantity`, `unit_price`, `legs`, `raw_legs`, `quote`, and `symbol`.

## Frozen Decimal Contract

| Type | Integer digits | Fractional digits | Sign |
| --- | --- | --- | --- |
| Money | 1–12 | 0–4 | Unsigned; maximum `999999999999.9999` |
| Quantity | Up to 18 | Up to 8 | Unsigned; zero allowed |
| UnitPrice | Up to 12 | Up to 8 | Unsigned; zero allowed |
| FxRate | Up to 8 | Up to 12 | Unsigned; greater than zero |

`rust_decimal` is declared as `rust_decimal = "1"` in `src-tauri/Cargo.toml` with no extra features. Valuation retains full checked `Decimal` precision and rounds only at Money boundaries using four fractional digits and midpoint-nearest-even.

Every existing financial value is unsigned. v0.1.4 introduces the first signed financial results in the product, so it must add new types rather than relaxing `Money`. Enabling the `rust_decimal` `maths` feature for `powd`, `ln`, and `exp` is a Phase 1 engineering deliverable; `f32`, `f64`, SQLite `REAL`, and JavaScript `number` remain prohibited for every financial value including return rates.

## Frozen Product Decisions

These are already approved in the [release contract](v0.1.4.md). They are frozen here so Phase 1 and later do not reopen them:

- Lot policy is FIFO only. There is no average-cost mode, no user lot selection, and no per-Instrument policy switch.
- Cost basis is a derived interpretation of the immutable Activity ledger. Analytics never post an Activity and never change current state, net worth, Quantity, or a snapshot.
- Origin and adjustment quantities remain unknown-basis until the user explicitly declares a basis. Nestworth never infers one from the first historical quote.
- Fees are never capitalized into cost basis. Gross and net gain are reported separately.
- No benchmark, index series, or peer comparison ships in v0.1.4.
- No live quote or FX vendor is selected or required. All analytics remain manually operable offline.
- Snapshots stay closed-day, append-only revisions produced only by explicit rebuild.
